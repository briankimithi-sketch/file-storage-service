# 1. Introduction

Software quality is one of the most important aspects of modern software development, especially within the banking industry where reliability, accuracy, security, and data integrity are critical. Even minor software defects can lead to financial losses, transaction failures, or security vulnerabilities.

One of the most effective techniques for improving software quality is **Unit Testing**. It allows developers to verify that each component of an application behaves as expected before it is integrated with other parts of the system.

During my internship at **ABC Bank**, I implemented extensive unit testing while developing the **Negotiated Rates System**, ensuring that the application's business logic, controllers, services, repositories, and utility components functioned correctly and consistently.

# 2. What is Unit Testing?

Unit Testing is a software testing technique in which individual units or components of an application—such as methods, classes, or functions—are tested independently to verify that they produce the expected results.

A unit test focuses on a single piece of functionality without depending on external services such as databases, APIs, messaging systems, or authentication servers.

Unit testing helps developers:

* Detect defects early in the development lifecycle.
* Reduce debugging costs.
* Build modular and maintainable software.
* Improve application reliability.
* Increase confidence when modifying existing code.

### Banking Example

In banking systems, unit testing is commonly used to verify:

* Interest calculations
* Loan eligibility rules
* Transaction validation
* Currency conversion
* Payment processing
* Account balance calculations
* Exchange rate negotiations

# 4. Unit Testing Process

The unit testing lifecycle consists of the following stages:

### Step 1: Identify the Unit

Select the function, class, or module to be tested and understand its expected behavior.

### Step 2: Design Test Cases

Develop test cases covering:

* Positive scenarios
* Negative scenarios
* Boundary conditions
* Exception handling
* Invalid inputs

### Step 3: Execute Tests

Run the tests using an appropriate testing framework.

### Step 4: Analyze Results

Determine which tests passed or failed and identify the cause of failures.

### Step 5: Fix Defects

Correct identified issues within the application code.

### Step 6: Re-run Tests

Execute the tests again to confirm that defects have been resolved.

### Step 7: Measure Coverage

Evaluate how much of the application code has been tested.

### Step 8: Continuous Integration

Automate test execution within the CI/CD pipeline to provide continuous quality assurance.

# 6. Unit Testing Architecture

A good unit testing architecture ensures software components are tested independently.

## Test Isolation

External dependencies such as:

* Databases
* APIs
* RabbitMQ
* Authentication servers
* File systems

are replaced using mock objects.

This ensures that only the business logic being tested influences the outcome.

---

## AAA Pattern

The project follows the Arrange–Act–Assert (AAA) testing pattern.

### Arrange

Prepare:

* Test objects
* Mock dependencies
* Input data

### Act

Execute the method under test.

### Assert

Verify that the expected results match the actual output.

This structure produces readable, maintainable, and reliable test cases.

# 8. Unit Testing in the Negotiated Rates Project

## Project Overview

The Negotiated Rates System enables bank users to negotiate foreign exchange rates before initiating transfers. The system manages the complete negotiation lifecycle, including rate requests, approvals, transfers, notifications, and data persistence.

To ensure reliability, a comprehensive testing strategy was implemented across multiple application layers.

---

## Controller Testing

Controller unit tests verified REST API behavior independently from the service layer.

The following controllers were tested:

* RateRequestController
* RateAcceptController
* TransferController
* AuthController
* MessageController
* RootController

These tests validated:

* HTTP status codes
* Request validation
* JSON responses
* Exception handling
* Endpoint behavior
* Controller-to-service interactions using mocked dependencies

---

## Service Layer Testing

The service layer contains the core business logic of the application.

The following services were tested:

* RateRequestService
* TransferService
* AppNotification

Major business scenarios covered included:

* Rate request creation
* Approval workflows
* Rejection workflows
* Currency conversion calculations
* Transfer creation
* Validation of negotiated rates
* Notification triggering
* Business rule enforcement
* Exception handling

Mockito was used extensively to isolate the service layer from repositories and external systems.

---

## Repository Integration Testing

Unlike controller and service tests, repository tests interacted with a real PostgreSQL database.

Repositories tested include:

* RateRequestRepo
* TransferRepo

These integration tests verified:

* Custom JPQL queries
* CRUD operations
* Data persistence
* Record retrieval
* Query correctness
* Entity relationships

Configuration used:

* `@DataJpaTest`
* `@AutoConfigureTestDatabase(replace = NONE)`
* PostgreSQL test schema (`nr_test`)

This ensured repository behavior accurately reflected production database interactions.

---

## Producer Testing

The RabbitMQProducer component was unit tested to verify:

* Message generation
* Queue publishing logic
* Producer behavior

without requiring an actual RabbitMQ server.

---

## Utility Testing

Utility classes were tested independently, including:

* HTTPSClient
* StringOperation

These tests verified helper methods used throughout the application.

---

## Configuration Testing

Configuration classes were also tested to verify application bean creation and configuration logic.

Components tested include:

* RabbitMQConfig
* OpenAPI30Configuration

# 10. Testing Strategy Implemented

The project adopted a mixed testing strategy consisting of unit testing and integration testing.

## Unit Tests

Frameworks:

* JUnit 5
* Mockito

Annotations used:

* `@ExtendWith(MockitoExtension.class)`
* `@Mock`
* `@InjectMocks`

These tests execute without loading the Spring Application Context, resulting in very fast execution.

### Components Covered

* Controllers
* Services
* Producers
* Utilities
* Configuration classes

---

## Integration Tests

Repository tests use:

* `@DataJpaTest`

with a real PostgreSQL database configured specifically for testing.

These tests validate:

* SQL queries
* Repository behavior
* Persistence
* Entity mapping

without loading the complete application.

| Layer             | Coverage                 |

Key implementation highlights include:

* Pure Mockito-based controller tests
* Pure Mockito-based service tests
* Real PostgreSQL repository testing
* No `@SpringBootTest` due to external infrastructure dependencies
* Mockito Inline Agent configured for JDK 21 compatibility
* Keycloak security isolated from unit tests through dependency mocking

This approach resulted in fast execution while maintaining strong confidence in application correctness.

# 14. Limitations of Unit Testing

Although highly beneficial, unit testing has limitations.

It does not:

* Test complete system integration
* Detect user interface issues
* Replace end-to-end testing
* Validate external infrastructure
* Guarantee absence of defects

Consequently, unit testing should be complemented by integration, system, and user acceptance testing.
